# Data Dictionary — Proposed Training Table

Status: **planning document, Phase 2**. Defines the fields a model-ready
training table is expected to need, based on the sources evaluated in
`docs/data_sources.md`. This is a **proposed schema**, not an
implemented one — no feature-engineering code exists yet, and the exact
column set will be refined once the ML pipeline (`ml-service/src/`) is
actually built against real data.

## Availability Legend

- **AVAILABLE** — a verified, accessible source for this field exists
  (see `docs/data_sources.md`); computing the field is an engineering
  task, not a sourcing risk.
- **TO VERIFY** — a plausible source exists but a detail needed to be
  fully confident (exact format, exact resolution, access mechanism,
  or license) was not confirmed in this research pass.
- **OPTIONAL** — a field that would add value if available but is not
  required for a first, honestly-scoped MVP model.
- **NOT AVAILABLE** — no credible source was identified in this research
  pass; the field is aspirational and must not be silently filled with
  invented values.

## Core Identity and Label Fields

| Field | Description | Source | Status |
|---|---|---|---|
| `zone_id` (now `grid_id`) | Identifier for the spatial unit the row describes. **Resolved in Phase 4**: a 1km x 1km grid cell, generated by `ml-service/src/features/grid.py::build_prediction_grid` — see `docs/training_dataset_build.md` §5 for the full resolution decision and reasoning (rainfall's ~25km native resolution vs. DEM/WorldCover's 10-30m was the deciding factor). | `ml-service/src/features/grid.py`, run against the real Kerala inventory's proxy study area | **AVAILABLE** — 42,620 real grid cells generated; the *administrative boundary* originally envisioned to inform this schema (geoBoundaries/GADM) is still NOT ACQUIRED, so the grid currently covers a proxy study area (buffered convex hull of the landslide points), not an authoritative Kerala boundary |
| `geometry` / `latitude`, `longitude` | Point or polygon reference for the zone/observation. | geoBoundaries / GADM (zone polygons); Hao et al. (2020) inventory (landslide point coordinates) | AVAILABLE |
| `timestamp` / `event_date` | Date (and where relevant, time) the row's features are computed *as of*, and — for positive examples — the landslide occurrence date. | Hao et al. (2020) inventory is tied to the August 2018 event | **TO VERIFY** — confirmed via the peer-reviewed paper's own text (Phase 3 research) that the inventory has **no per-record date field at all**, only a defined event window (1 June–26 Aug 2018). A prediction reference time T must be defined by a separate, documented method (see `docs/temporal_alignment.md`), not read from the inventory itself. |
| `target` | Binary landslide occurrence label for this grid cell. | Positives: real spatial join of the Hao et al. (2020) inventory onto the grid (2,139 of 42,620 cells). Negatives: buffered/stratified sampling per `docs/negative_sampling.md`, implemented in `grid.py::select_negative_grid_cells` | **PARTIALLY AVAILABLE** — positive labels are real and complete (verified: `positive_count` sums to exactly 4,728, matching the raw inventory exactly). A real candidate negative set (6,417 cells, 3:1 ratio) exists and passes spatial-leakage checks, but the sensitivity analysis required by `docs/negative_sampling.md` §3 has not been run, so this negative set is not yet finalized — see `docs/training_dataset_build.md` §8 |

## Historical / Contextual Features

| Field | Description | Source | Status |
|---|---|---|---|
| `historical_landslide_count` | Count of prior landslide events in or near this zone before the prediction date. | Derived from the landslide inventory itself | **NOT AVAILABLE for the MVP — explicitly excluded.** Phase 3's temporal-alignment analysis (`docs/temporal_alignment.md` §5) determined this is a concrete leakage risk given the single-event inventory (all positives share one ~3-month window, so any "prior count" computed from this same inventory is either trivially zero or risks counting same-window events as "history"). Revisit only if a second, independent, earlier-dated inventory is obtained. |
| `distance_to_road` | Distance from the zone/point to the nearest mapped road. | OpenStreetMap (Overpass API) | AVAILABLE, with the regional-completeness caveat noted in `docs/data_sources.md` §10.1 |
| `nearby_village_count` / `population_context` | Count/density of populated places near the zone, for exposure context (not a predictive feature for occurrence, but relevant to risk *communication*). | OpenStreetMap (Overpass API); Census of India as a stronger alternative | OpenStreetMap: AVAILABLE with completeness caveat. Census of India: **NOT AVAILABLE** (UNVERIFIED access — see `docs/data_sources.md` §9.2) |
| `nearby_critical_infrastructure` | Count/presence of schools, health facilities, etc. near the zone — for dashboard/communication context, not model training. | OpenStreetMap infrastructure tags | OPTIONAL / lower reliability than roads or villages — see `docs/data_sources.md` §11.1; explicitly Priority C |

## Explicit Non-Commitments

This dictionary intentionally does not:
- Assume every "TO VERIFY" field will resolve to AVAILABLE — some may
  turn out to require a different source, a coarser proxy, or exclusion
  from the first model iteration.
- Specify exact column data types, units, or null-handling conventions —
  these are implementation decisions for `ml-service/src/features/`,
  informed by whichever source is finally confirmed for each field.
- Claim `target` label quality is resolved — it is the single most
  consequential open item in this dictionary, because the negative-
  sampling method chosen will materially affect every downstream metric
  described in `docs/validation_strategy.md`.

This document will be revised once real data has actually been pulled
and inspected — at that point "AVAILABLE" fields should be reconfirmed
against the real file/API response, not assumed correct because they
were AVAILABLE in this research pass.
